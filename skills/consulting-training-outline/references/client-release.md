# 客户交付检查与文件制作

## 交付状态

- 工作草稿：关键输入缺失，可继续写作但不能对外定稿。
- 待业务复核：可写部分完成，但仍有事实、商务或责任待确认。
- 可供业务终审：证据齐全且内容和文件检查通过，等待公司指定负责人确认。
- 已确认客户交付版：只有当前版本已获用户或授权业务负责人明确确认，并通过内容与文件检查时使用。用户请求“直接交付”不是对未来未知报价、事实或条款的逐项批准；但已明确批准的内容不重复要求确认。

不用“保证可直接给客户”替代实际检查。原件是PDF时不可声称完全继承原生Word/PPT对象。

## 内容关口

以下任一未解决则不能标已确认客户交付版：
- 核心需求遗漏、范围或成果互相矛盾、工期资源明显不可行。
- 客户关键事实、案例、资质、人员能力或报价没有可靠依据。
- 合同义务、验收、付款触发、免费服务等尚有关键歧义。
- 金额/税口径/币种错误，主体错用，否决项未查明。
- 有未经验证的收益保证、虚假引用，或客户资料残留/误用。
- 文件无法打开、要求可编辑但以整页图片替代、重要内容被裁切。

所有应填的最终字段不能有TBD、占位符、TODO或“待确认”。缺项要在内部清单显式保留，不能靠删除字段掩盖必填要求。内部清单与客户正文分开；核心未决事项仍会阻断定稿。

## 形成文件

按用户指定格式生成原生可编辑文件；使用环境可用的相应文档/演示工具。技能本身不捆绑渲染器，不伪造已运行工具。工具缺失时完成内容并明确缺少文件生成/视觉验证，不将Markdown改扩展名冒充Office。

1. 在副本上工作，保留原模板；载入实际样式/母版，替换本次内容，删除不适用样例。
2. 核对标题层级、目录、页码、表格、交叉引用、附件编号、图表单位及来源。
3. 生成并重开最终可编辑源文件；另按用户要求导出PDF。不可只检查中间版本。
4. 渲染全部最终页面逐页查看：截断、重叠、跨页、空白页、缺字、字号、对齐、图片清晰度及表格可读性。模板本身有缺陷时在副本中修正并记录。
5. 核对隐藏页、备注、批注、修订、作者和其他元数据，清除与本次无关内容；不要删除用户要求保留的讲稿或有效审阅记录。
6. 修改后重渲染受影响页面，并重新检查目录及页码。不能用未渲染的早期截图代表最终质量。

## 客户包与内部包

客户包：当前批准的可编辑文件、要求的PDF及授权附件。内部包：输入基线、模板映射、证据台账、需求/成果映射、问题与修订记录、交付检查记录。不得把内部假设或敏感定价过程混进客户包。

建议保存 delivery-manifest.json，记录文件名、用途、版本、检查人/方法及检查结果；使用 [scripts/check_delivery.py](../scripts/check_delivery.py) 做机器可判定的辅助检查，命令见下。该脚本不验证事实真伪、法律适用或视觉品质，不能代替人工/模型专业审查。

```bash
python3 scripts/check_delivery.py /absolute/path/delivery-manifest.json
```

manifest格式与最小示例见 [manifest-example.json](manifest-example.json)。路径以manifest目录为基准，交付清单必须填写本次实际文件。脚本失败应修复原因而不是修改检查结果来通过。

manifest的review_checks逐项记录criterion、verdict（pass/fail/not-assessed/not-applicable）、version和evidence。未评估记录原因；定稿不得有fail/not-assessed，旧版本审查不能放行新稿。证据字段仅记录引用，脚本不确认其真实有效性。
