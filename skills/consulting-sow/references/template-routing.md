# SOW 模板与详略选择

同一 skill 内选择适合本项目的结构，不把所有 SOW 改成一个目录。不因原件长短而推断法律完备性，也不把历史协议自动当本次有效合同。

|模式|适用情形|主要结构|重点检查|
|---|---|---|---|
|简版项目协议|工作模块少、范围明确、主合同另行管理|双方信息→背景/目标→包含/排除→阶段工作→成果/周期/已确认商务→确认栏|不能因篇幅短漏掉验收、责任和变更；缺项列补充建议，不编合同条款|
|模块式范围说明|多个业务模块、有共创和试点/陪跑|目标→时间→分模块范围→计划→成果与商务→边界→验收|每模块承诺、试点、工作坊、辅导和成果可追溯，建议性成果与确定交付分开|
|复杂专项工作分解|架构、流程、数据或应用等多层设计|专项概述→分层任务和方法→阶段输出→交付汇总，衔接合同附件|按原模板工作分解层级逐项映射；工具/系统/数据能力需要验证，不能自动承诺开发实施|

选择时记录模板、版本、适用主体、主合同关系、匹配原因和不适用部分。用户明确模板优先；项目规模决定展开深度，不用固定页数限制。缺失关键合同条件保持待确认。

复杂任务需要将活动说明转成可验收成果：例如“进行流程诊断”应展开为诊断范围、输入、分析活动、报告内容和确认点，而非仅写方法名。历史中出现的流程挖掘、企业级模型等工具和工作项须验证本项目是否具备数据与实施条件。

方案与 SOW 配对时按需求和交付物 ID 对照目标、范围、周期、成果、排除、双方责任和商务条件；对齐的是本次批准基线，不要求两个文件逐字相同。发现“设计 vs 实施”“支持 vs 负责”“培训包含 vs 排除”差异，列给业务确认。

输出默认可编辑 Word；用户指定其他格式则遵从。PDF 样例仅提供重建参考，不代表已经取得原始合同模板、完整附录或签章授权。旧法规名称、主体名称、签章、日期、续费/赠送与自动验收措辞都须重新核验，不从历史文件自动沿用。
